# Inside the CPU: NVIDIA CUDA Lab

Runnable code from the [Inside the CPU: NVIDIA CUDA Lab](https://www.youtube.com/@TomJNet) video series: install and verify, the first kernel, grids, blocks and threads, device and unified memory, shared memory and tiling, synchronization, streams, memory coalescing, occupancy, Nsight and an honest CPU against GPU benchmark.
One folder per episode, one complete CUDA program per idea shown on the slides, plus the shell scripts that run the NVIDIA tools of the episode. It is the hands on half of [Inside the CPU: GPU Architecture Lab](https://github.com/tomjnet/inside-the-cpu-gpu-architecture-lab): there we drew the hardware, here we program it.

Before any kernel runs, three pieces of software have to agree with each other and with your GPU. This video separates the driver (kernel module plus libcuda, part of the GPU driver), the CUDA Toolkit (nvcc, headers, libraries and tools) and the runtime (libcudart, linked into your program), explains the one compatibility rule that matters and what compute capability means, and then verifies the machine in three steps: nvidia-smi, nvcc --version and a device query program. The last sample prints the environment you should keep next to every benchmark. Lab: Ubuntu 24.04, native or WSL 2 with the NVIDIA Windows driver, CUDA Toolkit 13, any NVIDIA GPU of the Turing generation or newer. | Your First CUDA Kernel in 8 Minutes | Episode 2 of the NVIDIA CUDA Lab. One .cu file holds code for two processors: nvcc sends the host code to g++ and compiles the functions marked for the device for the GPU. We write Hello GPU with the __global__ qualifier, launch it with the triple angle bracket syntax (blocks in the grid, threads per block), and find out why the program prints nothing when the synchronization is missing: a kernel launch is asynchronous and returns before the work is done. That decides where errors appear, so we build the two helpers that every later episode reuses, check and check_kernel, run a one element arithmetic kernel with every call checked, and then break it on purpose to see a launch error, an execution error and a sticky error. | CUDA Grids, Blocks and Threads in 8 Minutes | Episode 3 of the NVIDIA CUDA Lab. One kernel runs on thousands of threads, and every thread has to find the element it owns. We look at the shape of a launch (one grid of blocks of threads), build the global index from blockIdx, blockDim and threadIdx, round the number of blocks up on the host and guard the extra threads in the kernel, add two vectors of one million elements, move to two dimensions with dim3 to invert a small grayscale image held in a plain array, and see why block sizes are multiples of the warp size and what the limits of a launch are. Every sample checks its result on the CPU and prints PASS or FAIL. The grid, the guard and the warps are animated. | `03-cuda-lab-grids-blocks-threads-in-8-minutes` |
| CUDA Host and Device Memory in 9 Minutes | Episode 4 of the NVIDIA CUDA Lab. The GPU has its own memory, and nothing reaches it unless you put it there. This episode walks the explicit memory model of CUDA from left to right: allocate on the device with cudaMalloc, copy in both directions with cudaMemcpy, release with cudaFree, and wrap ownership in a small RAII class so no early return can leak a buffer. Then the host side of the copy: why pageable memory costs a hidden extra copy through a staging buffer of the driver, how pinned memory from cudaMallocHost lets the GPU read your buffer directly with DMA, and when pinning is worth it. Finally we time allocation, copies and kernel separately, with CUDA events for device time and steady_clock for host time, in one complete vector addition that is verified on the CPU. The two memories, the five step pattern and the pageable against pinned copy are animated. | `04-cuda-lab-host-and-device-memory-in-9-minutes` |
| CUDA Unified Memory in 7 Minutes | Episode 5 of the NVIDIA CUDA Lab. The vector addition of the previous episode, this time with no copies in the code: cudaMallocManaged returns one pointer that is valid on the host and on the device, and the pages behind it migrate to whoever touches them first. We see why the first kernel run pays for that migration and the warmed run does not, move the pages ahead of time with cudaMemPrefetchAsync and its cudaMemLocation argument, and handle a driver that refuses the hint, which is the normal case on Windows hosts and WSL. The page migration is animated, and every sample checks its result on the CPU. | `05-cuda-lab-unified-memory-in-7-minutes` |
| CUDA Shared Memory and Tiling in 9 Minutes | Episode 6 of the NVIDIA CUDA Lab. A kernel can keep a value in three places: a register, shared memory on the chip, or global memory far away. This episode manages the middle one by hand. We declare an array with the __shared__ qualifier (one copy per block, size fixed at compile time), load it cooperatively (every thread of the block copies one element of the tile), protect it with the __syncthreads() barrier before the use and before the next load, and use the pattern to tile a 512 by 512 matrix multiply with 16 by 16 tiles. The result is checked on the CPU, both kernels are timed with CUDA events, and the global memory reads are counted: 1024 per thread for the naive kernel, 64 for the tiled one. The tiling and the bank conflict figures are animated. | `06-cuda-lab-shared-memory-tiling-in-9-minutes` |
| CUDA Synchronization Without Deadlocks in 8 Minutes | Episode 7 of the NVIDIA CUDA Lab. The three levels at which a CUDA program waits: the threads of one block behind the __syncthreads() barrier, one stream behind cudaStreamSynchronize, and the whole device behind cudaDeviceSynchronize. We write a race on shared memory on purpose (256 threads adding into one cell), see why std::atomic does not compile in device code, and restructure the sum as a reduction with a halving stride. Then the deliberately racy reduction, the fix with one barrier per step, the one way to deadlock a barrier (inside a divergent branch or after an early return), and a validation loop that compares 100 runs with the CPU sum. The reduction and the deadlock are animated. | `07-cuda-lab-synchronization-in-8-minutes` |
| CUDA Streams and Asynchronous Copies in 10 Minutes | Episode 8 of the NVIDIA CUDA Lab. A stream is an ordered queue of copies and kernels, and two streams may run at the same time. With pinned host memory and the copy engines of the GPU, the upload of one chunk can overlap the kernel of another and the download of a third. We create streams, allocate pinned buffers, queue asynchronous copies, mark the queue with events for device timing and for dependencies between streams, and build a pipeline that pushes 8 chunks through upload, kernel and download, first on one stream, then on four, with the end to end time of both and a text timeline. Run the samples on your own GPU and read your own ratio: nothing here is a measurement we took. | `08-cuda-lab-streams-async-copies-in-10-minutes` |
| Memory Coalescing in CUDA in 8 Minutes | Episode 9 of the NVIDIA CUDA Lab. A warp of 32 threads reads global memory together, and the hardware answers in 32 byte sectors: when neighbouring threads read neighbouring addresses, 4 sectors serve the whole warp; when they do not, the same 128 bytes can cost 32 sectors. We write one gather kernel, feed it three index tables with identical arithmetic (coalesced, strided and scattered), time them with CUDA events, and then fix two layouts that hide a stride: an array of structures and a two dimensional index with x and y swapped. The access patterns are animated. | `09-cuda-lab-memory-coalescing-in-8-minutes` |
| CUDA Occupancy and Launch Configuration in 8 Minutes | How many threads per block? Episode 10 of the NVIDIA CUDA Lab reads the per SM budget from the device properties, asks a kernel what it needs with cudaFuncGetAttributes, lets the toolkit's occupancy calculator find the limiting resource, forces a register heavy kernel to 100 percent occupancy with launch bounds and watches it spill and slow down, and ends with a block size sweep from 32 to 1024 threads timed with CUDA events, printed as a table with the fastest configuration marked. | `10-cuda-lab-occupancy-launch-configuration-in-8-minutes` |
| Profile CUDA with NVIDIA Nsight in 10 Minutes | Profile before you optimize. We take the stream pipeline of episode 8, record it with Nsight Systems, read where the time goes with nsys stats, find the largest gap on the timeline, change exactly one thing and measure again, then zoom into one kernel with Nsight Compute. Along the way: CPU API time against GPU time, NVTX ranges that name the phases of a program, and why the first launch and the profiler itself must never be part of a result. The timeline before and after the change is animated. | `11-cuda-lab-profile-with-nsight-in-10-minutes` |

This episode builds a benchmark that can answer honestly: the same SAXPY on both sides, from 1 K to 16 M floats, with an -O2 CPU baseline instead of a strawman, CUDA events for kernel only time and steady_clock for end to end time, allocation, copies, launch and synchronization on the clock, warm up runs thrown away, the median and the p99 of repeated runs, and a CPU check of every GPU result before any number is printed. Then the size sweep finds the break even point, and batching shows how many small jobs become one large one. ## The lab

- Ubuntu 24.04, native or WSL 2 with the NVIDIA Windows driver (never install a Linux GPU driver inside WSL), CUDA Toolkit 13, any NVIDIA GPU of the Turing generation or newer.
- Every `.cu` program checks each runtime call, verifies its result on the CPU and ends with `PASS` or `FAIL`. Without a CUDA device it says so and exits 0.
- Every timing program prints its own numbers for the machine it runs on and never fails because of them. Sizes are small on purpose: they fit a 4 GiB laptop GPU.

## Python twins

Next to every program sits its Python twin, `NN_name.py`, that teaches the same idea in Python: the CUDA ones compile the same kernel text at run time with NVRTC through NVIDIA's cuda-python and run it on the GPU (`pip install cuda-python numpy`); without the libraries or a GPU they say so and exit 0. Run one with `python3 NN_name.py`, or all of them with `make py` (`make run` runs the compiled samples and then the Python ones; on Windows the Makefile calls `python`).

## Build and run

```bash
nvidia-smi
nvcc --version
```

Every folder has the same Makefile: `.cu` files build with `nvcc`, `.cpp` files with `g++`.

```bash
cd 03-cuda-lab-grids-blocks-threads-in-8-minutes
make            # build everything
make run        # build and run every sample
make clean
```
